# Групповые проекты по системному администрированию

**Дисциплина:** DevOps и системное администрирование  
**Состав:** группы по 5 человек  
**Формат:** командный проект; итог — общий стенд «компании», совместный game day и индивидуальная защита вклада

Три группы строят три части одной инфраструктуры и зависят друг от друга, как отделы в реальной компании:

| Группа | Условное название | Что строит |
|---|---|---|
| 1 | **Наблюдаемость и безопасность** (Observability & SecOps) | Сбор, хранение и анализ логов и метрик со всего «прода», обнаружение атак |
| 2 | **Инфраструктура и отказоустойчивость** (Infra & Resilience) | Диски и RAID, кластер ClickHouse + ZooKeeper, отработка отказов дисков, узлов, сети, стойки и ДЦ |
| 3 | **Корпоративная идентификация** (Identity & Corporate IT) | Единая учётная запись: LDAP + Keycloak, вход на серверы по SSH и во все веб-системы стенда |

## 1. Общие правила для всех групп

1. **ОС** — Debian 13. Стенд — виртуальные машины (KVM/Proxmox VE) или системные контейнеры Incus. Физических серверов и дисков нет: диски — виртуальные диски ВМ или loop-устройства.
2. **Всё как код.** Каждая машина и служба разворачивается ролями Ansible из Git-репозитория. Ручная настройка «на живом сервере» не засчитывается. Проверка: стенд пересоздаётся с нуля одной командой.
3. **Репозиторий.** До готовности GitLab группы 3 — любой доступный GitLab/GitHub; после — переезд в корпоративный GitLab.
4. **Документация** — в Markdown в репозитории: схема стенда (PlantUML или Mermaid), IP-план и DNS-имена, ранбуки, отчёты по проверкам. Скриншоты не являются доказательством — прикладывайте команды и их вывод.
5. **Внутренний домен** — `corp.internal`. DNS, время (chrony) и внутренний центр сертификации предоставляет группа 3; до этого — временно `/etc/hosts`.
6. **Единый вход везде.** Люди входят в любую систему стенда только под корпоративной учётной записью группы 3:
   - на серверы — по SSH через SSSD;
   - в веб-интерфейсы — через Keycloak: напрямую по OIDC, если система это умеет, иначе через oauth2-proxy перед интерфейсом;
   - в ClickHouse — через LDAP.

   Права определяются группами LDAP. Локальные учётные записи допустимы только как аварийный вход (break-glass) и для служебных подключений между системами. Такие записи технические, с минимальными правами, их секреты не хранятся в Git.
7. **Эксперименты с отказами** запускаются только скриптами с автоматическим откатом (например, `systemd-run --on-active=10min` снимает правила `tc`/`nft`), чтобы не потерять доступ к стенду. Доступ к консоли ВМ в обход сети — обязателен.
8. **ИИ-ассистенты** разрешены. Ведите журнал: что спросили, что получили, чем проверили. У агентов — только чтение, никаких прав на изменение стенда без человека.

## 2. Группа 1. Наблюдаемость и безопасность

### Цель

Построить общую систему логирования, метрик и обнаружения атак для всей «компании». Логи и метрики всех машин всех трёх групп и микросервисов должны стекаться в единые хранилища. Логи — в формате ECS (Elastic Common Schema). Всё должно искаться, визуализироваться, порождать оповещения и быть доступно только по корпоративным учётным записям.

### Архитектура

```
микросервисы, хосты групп 1–3
   │  Vector (агент): journald, файлы, docker, auditd → ECS (VRL)
   │  vmagent: node_exporter, метрики сервисов, ClickHouse, ZooKeeper, mdadm
   ▼                                   ▼
Redpanda — буфер логов                VictoriaMetrics — хранилище метрик
(logs-app, logs-system, logs-security)  vmalert → Alertmanager → каналы групп / Mailpit
   ▼
Vector (агрегатор)
   ├──► Loki       — все логи, метки: service, host, env, level
   └──► Manticore  — полнотекстовый индекс ECS-документов
              ▼
Grafana: Loki + Manticore (источник MySQL) + VictoriaMetrics

Вход людей: Grafana — OIDC через Keycloak;
Redpanda Console, vmui, Alertmanager — через oauth2-proxy + Keycloak
```

### Обязательный минимум

1. **Микросервисы.** Не менее двух (лучше три) микросервисов, которые реально общаются между собой (например: `gateway` → `orders` → PostgreSQL). Требования:
   - логи в JSON с полями `trace.id` и `service.name`;
   - эндпоинт `/metrics`;
   - управляемое внедрение ошибок: доля 5xx и задержка задаются переменной окружения;
   - генератор нагрузки (k6 или аналог), который работает постоянно.
2. **Сбор.** Роль Ansible с агентами Vector, node_exporter и vmagent для всех хостов всех трёх групп. Источники логов: journald, файлы приложений, логи контейнеров, auditd. У Vector и vmagent включены дисковые буферы.
3. **ECS-нормализация.** Каждый документ содержит как минимум `@timestamp`, `host.name`, `service.name`, `log.level`, `event.dataset`, `message`; события безопасности — поля `event.category`, `event.action`, `user.name`, `source.ip`.
4. **Redpanda** — буфер между сбором и хранилищами логов: 3 брокера, отдельные топики по типам логов, срок хранения, контроль отставания потребителей (`rpk group describe`). Производители и потребители подключаются под отдельными служебными учётными записями SASL/SCRAM.
5. **Хранилища логов:**
   - Loki — все логи; ограничение числа меток (никаких `trace.id` или `user.name` в метках);
   - Manticore — ECS-документы приложений и безопасности для полнотекстового поиска;
   - сроки хранения и объёмы задокументированы;
   - API хранилищ закрыты от прямого доступа людей: только сеть стенда и служебные учётные записи.
6. **Метрики — VictoriaMetrics:**
   - vmagent собирает метрики со всех хостов, микросервисов, а также ClickHouse, ZooKeeper и mdadm группы 2, и отправляет их в VictoriaMetrics (single-node);
   - задан срок хранения;
   - правила оповещений выполняет vmalert, маршрутизацию уведомлений — Alertmanager;
   - запросы на MetricsQL; кардинальность контролируется через Cardinality explorer в vmui.
7. **Grafana:**
   - дашборд RED по каждому микросервису (запросы, ошибки, задержка);
   - дашборд USE по хостам;
   - дашборд безопасности;
   - дашборды для групп 2 и 3: RAID, репликация ClickHouse, ZooKeeper, входы в системы;
   - сквозной поиск запроса по `trace.id`.
8. **Безопасность (EDR/HIDS):** auditd (с Laurel для JSON), а также Falco или osquery на хостах; события — в топик `logs-security`. Не менее пяти правил обнаружения с оповещением:
   - перебор паролей SSH;
   - `sudo` пользователем не из разрешённой группы;
   - создание пользователя или изменение `/etc/passwd`, `/etc/sudoers`, `/etc/ssh/sshd_config`;
   - появление нового SUID-файла;
   - запуск оболочки с сетевым подключением (обратная оболочка) или исполняемого файла из `/tmp`.
9. **Оповещения:** не менее 8 правил (сервисы, хосты, безопасность, RAID и кластер группы 2, входы группы 3); у каждого есть ранбук и проверка «сработало — сбросилось».
10. **Единый вход во все свои системы:**
    - Grafana — OIDC через Keycloak; `grp-observability` и `admins` получают Admin/Editor, остальные — Viewer;
    - Redpanda Console, vmui, Alertmanager — за oauth2-proxy с Keycloak; доступ только для `grp-observability` и `admins`;
    - аварийный локальный администратор Grafana описан в ранбуке, его пароль хранится вне Git.

### Проверки приёмки

| № | Проверка | Критерий |
|---:|---|---|
| 1 | Задержка доставки логов: событие на хосте → видно в Grafana | p95 ≤ 30 с, измерено |
| 2 | Полнота ECS | 100 % документов за час содержат обязательные поля (запрос с подсчётом) |
| 3 | Сквозной запрос | По одному `trace.id` находится путь запроса через все сервисы в Loki и в Manticore |
| 4 | Метрики | В VictoriaMetrics есть все хосты трёх групп; запрос за 7 суток работает; посчитан расход диска на один сэмпл |
| 5 | Кардинальность | Число потоков Loki и число временных рядов VictoriaMetrics задокументированы; топ-10 «тяжёлых» метрик и меток разобраны |
| 6 | Обнаружение атак | 5 сценариев из п. 8 выполняет другая группа или преподаватель; оповещение приходит ≤ 2 мин |
| 7 | Ложные срабатывания | За сутки нормальной работы нет ложных оповещений безопасности (или каждое разобрано) |
| 8 | Единый вход | Матрица доступа по Grafana, Redpanda Console, vmui, Alertmanager совпадает с ожидаемой; уволенный пользователь не входит никуда |

### Сценарии отказов (все 8 обязательны)

1. Loki остановлен на 10 минут под нагрузкой → после запуска потерь нет: число событий в хранилище совпадает с числом сгенерированных.
2. Manticore остановлен на 10 минут → потерь нет.
3. Отказ одного брокера Redpanda → сбор продолжается, отставание потребителей рассасывается.
4. VictoriaMetrics остановлена на 10 минут → vmagent буферизует данные на диск; после запуска в рядах нет пропусков.
5. Сеть между агентом и Redpanda разорвана на 10 минут → Vector копит события в дисковом буфере и догружает без потерь.
6. Диск хранилища логов заполнен до 95 % → оповещение приходит раньше отказа; поведение при полном диске и действия по ранбуку зафиксированы.
7. Шторм логов: один сервис увеличивает объём логов в 50 раз → ограничения (лимиты скорости в Vector, лимиты Loki) защищают остальные сервисы, данные которых не теряются.
8. Отказ Keycloak → что перестаёт работать (новые входы в Grafana и за oauth2-proxy), что продолжает (сбор, хранение, оповещения); аварийный вход работает.

Формат отчёта по сценарию — как у группы 2 (раздел 3).

### Роли в группе

1. **Сервисы и сбор** — микросервисы, нагрузка, роль агентов Vector, ECS-нормализация.
2. **Логи** — Redpanda, агрегатор Vector, Loki, Manticore, сроки хранения, сценарии 1–3, 5–7.
3. **Метрики** — vmagent, VictoriaMetrics, vmalert, Alertmanager, сценарий 4.
4. **Визуализация и доступ** — Grafana, дашборды, oauth2-proxy, единый вход, сценарий 8.
5. **Безопасность** — auditd, Falco/osquery, правила обнаружения, сценарии атак.

### Продвинутый уровень (по желанию)

- Кластер VictoriaMetrics (vminsert, vmselect, vmstorage с `replicationFactor=2`) и проверка отказа узла хранения.
- Трассы OpenTelemetry → Tempo; переход из лога к трассе в Grafana.
- Копия логов из Redpanda в ClickHouse группы 2 для аналитики (движок Kafka + материализованное представление).

## 3. Группа 2. Инфраструктура и отказоустойчивость

### Цель

Построить отказоустойчивую платформу данных с моделью «дата-центров, стоек и коммутаторов» и научиться ломать и восстанавливать её на всех уровнях: диски, RAID, узлы, сеть, стойка, ДЦ. Каждое утверждение об устойчивости должно быть подтверждено экспериментом с измерениями.

### Архитектура

- **Топология:** три «ДЦ» (`dc1`, `dc2`, `dc3`). Каждый ДЦ — отдельный Linux-мост («коммутатор») и подсеть; между ДЦ — маршрутизатор-ВМ («WAN»).
- **ZooKeeper:** 3 узла, по одному в каждом ДЦ.
- **ClickHouse:** 3 шарда × 2 реплики = 6 узлов. Реплики одного шарда — в разных ДЦ (шард 1: dc1 + dc2; шард 2: dc2 + dc3; шард 3: dc3 + dc1).
- **Хранилище каждого узла ClickHouse:** 4–6 виртуальных дисков по 5–10 ГБ → mdadm (RAID 10, 5 или 6 — на разных узлах разные уровни для сравнения) → LVM → XFS → `/var/lib/clickhouse`.
- **Нагрузка:** отдельная ВМ с генератором вставок и запросов через Distributed-таблицы.

### Обязательный минимум

1. **Стенд как код:** роли Ansible для сети (мосты, маршрутизация), дисков, ZooKeeper, ClickHouse, генератора нагрузки. Пересоздание с нуля одной командой.
2. **Диски и RAID:**
   - массивы mdadm с внутренним битмапом записи;
   - `mdadm.conf` и `update-initramfs` — массивы собираются после перезагрузки;
   - `mdadm --monitor` с уведомлением в систему группы 1;
   - LVM и XFS; замер `fio` для RAID 10, 5 и 6 на одинаковом профиле нагрузки.
3. **ZooKeeper:** ансамбль из трёх узлов; разрешённые команды `mntr`, `ruok`, `srvr`; метрики для vmagent группы 1; доступ к портам только от узлов ClickHouse и мониторинга.
4. **ClickHouse:**
   - кластер в `remote_servers` (3 × 2), макросы шарда и реплики, подключение к ZooKeeper;
   - таблицы ReplicatedMergeTree и Distributed;
   - эндпоинт метрик Prometheus;
   - постоянная нагрузка: вставки и аналитические запросы.
5. **Единый вход в ClickHouse:**
   - пользователи ClickHouse — корпоративные учётные записи через LDAP-каталог пользователей с сопоставлением групп LDAP ролям;
   - `grp-infra` и `admins` → роль администратора кластера, `grp-observability` → роль только для чтения;
   - генератор нагрузки и Grafana работают под отдельными техническими пользователями с минимальными правами;
   - на серверы — по SSH через SSSD.
6. **Скрипты хаоса** в репозитории: каждый сценарий — отдельный скрипт с параметрами, журналом действий и гарантированным откатом.

### Проверки приёмки

| № | Проверка | Критерий |
|---:|---|---|
| 1 | Воспроизводимость | Стенд пересоздан с нуля из репозитория на глазах у преподавателя |
| 2 | Кластер | `system.clusters` показывает 3 × 2; у всех реплик `is_readonly = 0`; данные через Distributed попадают во все шарды |
| 3 | Перезагрузка | После перезагрузки любого узла массивы, LVM и ClickHouse поднимаются сами |
| 4 | Сравнение RAID | Таблица RAID 10 / 5 / 6: IOPS и задержка (`fio`), время перестройки, число переживаемых отказов, полезный объём, рекомендация |
| 5 | Согласованность | После каждого сценария число строк на репликах каждого шарда совпадает |
| 6 | Доступ к ClickHouse | Вход под корпоративными учётными записями с ролями по группам; пользователь с ролью «только чтение» не может вставлять данные; уволенный пользователь не входит |
| 7 | Наблюдаемость | Отказы видны на дашборде группы 1 и порождают оповещения (mdadm, репликация, ZooKeeper) |
| 8 | Безопасность экспериментов | Каждый скрипт хаоса откатывается автоматически по таймеру |

### Сценарии отказов (8 из меню)

Выполнить **8 сценариев**, из них **обязательны № 4, 8 и 12**. Из каждого блока — не менее двух.

**Диски и RAID**

1. Отказ диска: `mdadm --fail` → `--remove` → добавить новый диск → перестройка под нагрузкой. Замерить время перестройки и влияние на задержку вставок при разных `sync_speed_min/max`.
2. «Выдернуть» диск на живой ВМ (`virsh detach-disk` или удаление SCSI-устройства через `/sys`) и вернуть новый.
3. Нестабильный диск: device-mapper `dm-flakey` или `dm-error` под одним из участников массива — когда mdadm исключает диск, что видно в `dmesg` и в мониторинге.
4. **Отказ двух дисков:** RAID 6 выживает, RAID 5 — нет, RAID 10 — зависит от того, какие именно. Для погибшего массива — восстановить узел ClickHouse: пересоздать хранилище и дождаться, пока реплика догрузит данные с соседней; при потере метаданных в ZooKeeper — `SYSTEM RESTORE REPLICA`.

**Узлы и координация**

5. Жёсткое выключение узла ClickHouse под нагрузкой: продолжаются ли вставки и запросы через Distributed; как догоняет реплика после включения (`system.replicas`: `absolute_delay`, `queue_size`).
6. Отказ лидера ZooKeeper: время выбора нового лидера, ошибки вставок.
7. Потеря кворума ZooKeeper (2 из 3): реплицируемые таблицы переходят в режим только для чтения — зафиксировать ошибки, поведение чтений и восстановление.

**Сеть**

8. **Деградация WAN между ДЦ:** `tc netem` — задержка 50–300 мс с разбросом, потери 1–10 %, повреждение и перестановка пакетов. Замерить задержку запросов и отставание репликации.
9. Разрыв связности: изоляция одного узла ClickHouse от ZooKeeper через `nftables` при сохранении связи с клиентами. Что происходит со вставками на этот узел?
10. Асимметричный разрыв (пакеты проходят только в одну сторону) и «чёрная дыра» из-за неверного MTU.
11. Отказ «коммутатора»: мост ДЦ опущен (`ip link set <bridge> down`) — эквивалент отказа стойки.

**Площадка**

12. **Отказ целого ДЦ:** все узлы одного ДЦ выключены. Какие шарды доступны, работает ли кворум ZooKeeper, что со вставками?
13. Отказ двух ДЦ из трёх: что обязано перестать работать и почему это правильно (защита от split-brain).

### Формат отчёта по сценарию (общий для всех групп)

Для каждого сценария в Markdown:

- гипотеза («ожидаем, что…»);
- точные команды внедрения и отката;
- наблюдения: метрики, логи, выдержки команд (`/proc/mdstat`, `system.replicas`, `mntr`, `ss`, `mtr` и т. п.);
- измерения: время обнаружения, время восстановления, доля ошибочных операций, p95 задержки, отставание;
- проверка отсутствия потерь и согласованности данных после восстановления;
- вывод и ранбук: что делать дежурному.

Итоговый документ группы 2 — **матрица отказов**: сценарий × что пострадало × что выжило × время восстановления × ручные действия.

### Роли в группе

1. **Сеть и топология** — мосты-«коммутаторы», маршрутизация между ДЦ, сетевые сценарии.
2. **Хранилище** — mdadm, LVM, XFS, `fio`, дисковые сценарии, сравнение RAID.
3. **ClickHouse** — шарды, реплики, Distributed, нагрузка, вход по LDAP и роли, согласованность данных.
4. **ZooKeeper** — ансамбль, метрики, сценарии кворума.
5. **Хаос-инженер** — скрипты сценариев с откатом, измерения, матрица отказов.

### Продвинутый уровень (по желанию)

- Замена ZooKeeper на ClickHouse Keeper и сравнение поведения при тех же отказах.
- Резервное копирование ClickHouse (`clickhouse-backup` или `BACKUP ... TO`) и восстановление после потери шарда целиком.
- Все 13 сценариев меню плюс заполнение файловой системы до 100 % и исчерпание inode.

## 4. Группа 3. Корпоративная идентификация

### Цель

Сделать «как в компании с Active Directory»: одна учётная запись на человека даёт вход на серверы по SSH, в GitLab, OpenProject и во все системы групп 1 и 2. Права определяются группами. Увольнение сотрудника в одном месте закрывает доступ везде.

### Ограничения продуктов, которые определяют архитектуру

- **OpenProject Community** умеет входить только через LDAP. SSO через OpenID Connect и синхронизация LDAP-групп — функции Enterprise.
- **GitLab CE** умеет и LDAP, и OpenID Connect. Синхронизация групп из LDAP — платная функция.
- Поэтому **источник истины — LDAP**, а Keycloak работает поверх него через LDAP User Federation и выдаёт OIDC для GitLab, Grafana и oauth2-proxy. Пароль, изменённый в одном месте, должен работать везде.

### Архитектура

```
DNS (corp.internal) + внутренний CA + chrony
            │
OpenLDAP (основной + реплика) — источник истины:
пользователи, группы, SSH-ключи, правила sudo
   ├──► SSSD на всех хостах групп 1–3 → вход по SSH, sudo по группам
   ├──► OpenProject CE → вход через LDAP
   ├──► ClickHouse группы 2 → вход через LDAP, роли по группам
   └──► Keycloak (PostgreSQL) → LDAP User Federation + синхронизация
              ├──► GitLab CE → OIDC (+ LDAP как запасной вход)
              └──► Grafana и oauth2-proxy группы 1 → OIDC, группы в токене
Почта для уведомлений: Mailpit
```

### Обязательный минимум

1. **Базовые службы:**
   - DNS-зона `corp.internal` (BIND 9 или Unbound) для всех хостов трёх групп;
   - внутренний центр сертификации (step-ca или OpenSSL) и TLS для всех веб-служб и LDAP;
   - chrony на всех хостах.
2. **OpenLDAP:**
   - структура `ou=people`, `ou=groups`, `ou=sudoers`, `ou=services`;
   - оверлеи `memberof`, `refint`, `ppolicy`;
   - схемы `posixAccount`/`posixGroup`, `openssh-lpk` (атрибут `sshPublicKey`), sudo;
   - только защищённые соединения (LDAPS или StartTLS);
   - технические учётные записи служб с правом только на чтение — отдельная для каждой системы;
   - **реплика** (syncrepl) на втором узле;
   - резервное копирование `slapcat`.
3. **Учётные записи:** все 15 студентов и преподаватели. Группы `grp-observability`, `grp-infra`, `grp-identity`, `admins`, `teachers`. Скрипт или плейбук заведения, отключения и принудительного сброса пароля пользователя.
4. **SSSD на всех хостах всех групп** (роль Ansible для групп 1 и 2):
   - идентификация и аутентификация через LDAP с обоими серверами в списке;
   - `access_provider = ldap` с фильтром по группе: студент заходит только на хосты своей группы, `admins` — везде;
   - `sudo` из LDAP по группам;
   - SSH-ключи из LDAP через `sss_ssh_authorizedkeys`;
   - автоматическое создание домашнего каталога.
5. **Keycloak:**
   - realm `corp`;
   - LDAP User Federation с выбранным и обоснованным режимом (`WRITABLE` или `READ_ONLY`), маппер групп, периодическая полная синхронизация и синхронизация изменений;
   - политика паролей;
   - OTP (второй фактор) обязателен для группы `admins`;
   - группы пользователя передаются в токене;
   - OIDC-клиенты для GitLab, Grafana и oauth2-proxy группы 1.
6. **GitLab CE:**
   - вход через Keycloak (OpenID Connect) с автоматической привязкой к существующему пользователю;
   - LDAP как запасной способ входа;
   - администраторы GitLab — члены группы `admins`;
   - репозитории всех трёх групп переезжают сюда.
7. **OpenProject CE:**
   - LDAP-подключение с фильтром по группам и автоматическим созданием пользователя при первом входе;
   - проекты для трёх групп.
8. **Скрипт проверки матрицы доступа.** Для набора тестовых пользователей скрипт пробует войти во всё: SSH на хосты каждой группы, `sudo`, Keycloak, GitLab, OpenProject, Grafana, Redpanda Console, vmui, Alertmanager, ClickHouse. Результат — таблица «пользователь × система × разрешено/запрещено» в сравнении с ожидаемой. Скрипт запускается по расписанию и сообщает о расхождениях в систему группы 1.

### Проверки приёмки

| № | Проверка | Критерий |
|---:|---|---|
| 1 | Базовые службы | Все хосты трёх групп разрешают имена `corp.internal`, время синхронизировано; все веб-службы и LDAP работают только по TLS с сертификатами внутреннего CA |
| 2 | SSSD | Установлен на всех хостах всех групп; вход по SSH только на хосты своей группы; `sudo` по правилам из LDAP |
| 3 | Матрица доступа | Фактическая матрица по всем системам всех групп совпадает с ожидаемой |
| 4 | GitLab | Вход через Keycloak и запасной вход через LDAP; учётная запись одна, без дублей |
| 5 | OpenProject | Вход через LDAP; пользователь не из разрешённых групп войти не может |
| 6 | MFA | Для `admins` второй фактор обязателен во всех системах с единым входом |
| 7 | Репликация LDAP | Изменение на основном сервере появляется на реплике ≤ 1 мин; состояния реплик совпадают (`contextCSN`) |
| 8 | Аудит | События входов Keycloak, LDAP и `auth.log` всех хостов видны у группы 1 |

### Сценарии жизненного цикла и отказов (все 8 обязательны)

1. **Приём на работу:** пользователь заведён одной командой → в течение 5 минут работают SSH на хосты своей группы, `sudo` по правилам, GitLab, OpenProject, Grafana, ClickHouse; матрица доступа совпадает с ожидаемой.
2. **Разграничение:** студент группы 2 пытается зайти на хост и в системы группы 3 → отказ; попытки видны у группы 1.
3. **Смена пароля** в Keycloak (или в LDAP) → новый пароль работает для SSH, OpenProject, GitLab, ClickHouse; старый — нигде.
4. **Увольнение:** пользователь отключён в LDAP → доступ закрыт во всех системах трёх групп. Время закрытия по каждой системе измерено с учётом кэша SSSD и синхронизации Keycloak; активные сессии Keycloak отозваны.
5. **Компрометация учётной записи:** принудительный сброс пароля, отзыв всех сессий и удаление SSH-ключа → доступ злоумышленника закрыт везде за ≤ 5 минут; действия зафиксированы в журнале.
6. **Отказ основного LDAP-сервера** → SSSD, Keycloak, OpenProject и ClickHouse переключаются на реплику без ручных действий; после восстановления основного данные сходятся.
7. **Отказ Keycloak** → GitLab пускает через LDAP, SSH, OpenProject и ClickHouse не затронуты; единый вход в веб-системы недоступен — это ожидаемо и описано в ранбуке.
8. **Ротация TLS-сертификатов** LDAP и Keycloak до истечения срока без простоя: клиенты продолжают работать, старый сертификат отозван.

Формат отчёта по сценарию — как у группы 2 (раздел 3).

### Роли в группе

1. **Базовые службы** — DNS, CA, chrony, общие роли Ansible, ротация сертификатов.
2. **Каталог** — OpenLDAP: схемы, оверлеи, TLS, ACL, репликация, резервное копирование, скрипты жизненного цикла пользователя.
3. **Keycloak** — realm, федерация LDAP, MFA, OIDC-клиенты для GitLab, Grafana и oauth2-proxy.
4. **Хосты** — SSSD, PAM, sudo, SSH-ключи; роль для групп 1 и 2; подключение ClickHouse группы 2 к LDAP.
5. **Приложения** — GitLab CE, OpenProject CE, Mailpit, скрипт матрицы доступа.

### Продвинутый уровень (по желанию)

- Kerberos и вход по SSH без пароля по билету (как в AD).
- Синхронизация групп в GitLab без платной функции: скрипт по API GitLab, раскладывающий пользователей по группам из LDAP.
- Вход по SSH через Keycloak: короткоживущие SSH-сертификаты (например, step-ca с OIDC).

| Группа 2 | Эндпоинты метрик ClickHouse, ZooKeeper, mdadm | группе 1 | начало этапа 3 |
| Группа 2 | Расписание и журнал экспериментов с отказами | группе 1 | этап 3 |

Интерфейсы фиксируются в репозитории файлом `CONTRACT.md` у каждой группы: адреса, порты, имена, форматы, ответственные. Изменение интерфейса — через merge request с согласованием другой группы.

## 6. Game day (финальное занятие)

1. **Группа 2** по заранее закрытому от других сценарию ломает инфраструктуру: диски, узлы, сеть, «ДЦ».
2. **Группа 3** проводит учебную атаку: перебор паролей, попытка входа уволенного сотрудника, `sudo` не по правам, вход скомпрометированной учётной записью.
3. **Группа 1** обнаруживает всё по дашбордам и оповещениям и ведёт инцидент: хронология, первопричина.
4. Каждая группа доступна другим только через корпоративные учётные записи группы 3.
5. **Итог:** безоценочный разбор каждого инцидента в Markdown — хронология, что обнаружили, за сколько, что не обнаружили и почему, действия по улучшению.
